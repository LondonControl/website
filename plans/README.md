## Dependency notes

- **001 has no hard dependents but should land first in practice** — it's
  the only plan that restores real CI signal; every other plan benefits
  from being reviewable against a working pipeline rather than a
  pre-broken one.
- **009 (Next.js upgrade)** lists 001 as a soft dependency because the new
  Next version's Node engine requirement only has real CI coverage once
  001 drops the Node 14.x/16.x matrix legs — 009 can still be executed and
  verified locally before 001 lands, it just won't have CI confirmation
  until both are in.
- **006 and 007 both touch files 002 also touches** (`login.tsx` and
  `forgot-password.tsx`), in different, non-overlapping regions. Both
  locate their targets by content match, not line number, so order isn't
  strictly required, but **running 002 first is recommended** — see each
  plan's own header for details.
- **011 (useApiForm hook) hard-depends on 003** — it refactors the
  post-003 (bug-fixed) version of the three ProfileForms; its "Current
  state" excerpts will not match the pre-003 code.
- **014 (useAuth loading-redirect fix) and 017 (CSRF consistency) both
  touch `useAuth.ts`**, in different regions from each other and from 002
  — all three can run in any order, but each plan's drift check is
  written to tolerate the others having landed first.
- **021 (Logout-all button) softly overlaps 017** (same file,
  `ActiveSessionsForm.tsx`, different functions — `logoutSession` vs. a
  new `logoutAllSessions`). Either order works; 021's steps assume 017's
  `csrf` import may or may not already be present and handle both cases.
- **020 (expanded test coverage) extends test files created by 004 and
  008** but works whether or not those have run yet (creates the files
  fresh if needed, extends them if not).
- **003, 004, 005, 008, 010, 012, 013, 015, 016, 018, 019 are otherwise
  independent** of every other plan in this batch — safe to execute in
  any order, including in parallel by different executors, subject to the
  soft file-overlap notes above where applicable.
- **Two plans require action outside this repository before they can be
  marked done, not just written**: 018 and 021 both make a code change
  that depends on an assumption about backend behavior the frontend repo
  can't confirm alone. Both plans build in a mandatory manual
  backend-verification step and explicit `BLOCKED` status guidance if that
  verification can't happen — don't let an executor mark either `DONE`
  without it.

## Findings NOT turned into plans

Everything from the original audit table has a plan. These are the small
number of things noted *inside* a plan's scope as deliberately deferred
follow-up, rather than being worth a standalone plan of their own — kept
here too so they aren't lost:

- **The `data.data.images` mutate-during-render pattern in
  `products/[id].tsx`** (plan 019 fixes the crash risk around it, not the
  underlying mutation style) — a future refactor could compute a derived,
  non-mutated `images` array instead.
- **`ActiveSessionsForm.tsx`'s direct SWR-cache mutation**
  (`data.data.splice(...)` inside `logoutSession`) — noted in plan 017's
  scope as a separate anti-pattern, not fixed there.
- **Table column definitions and page-level table integration tests**
  (`OrdersColumns`/`DownloadsColumns` formatting/sorting logic,
  `orders/index.tsx`/`downloads.tsx`/`profile.tsx` page-level tests) —
  explicitly flagged as out of scope in plan 020's "Maintenance notes";
  real gap, sized as its own future plan rather than bolted onto 020.
- **README.md deploy-instructions accuracy** (still describes Netlify/
  static-export deployment left over from the original boilerplate
  template) — noted in plan 012's "Maintenance notes" as the docs-cleanup
  counterpart to that plan's build-script fix; not itself a P1-P3 code
  fix, so no standalone plan.
- **Backend-side fixes** implied by plans 018 and 021, if their manual
  verification steps reveal the frontend's assumption about backend
  behavior is wrong — by definition can't be planned from this repo; each
  plan's STOP conditions say to escalate rather than guess.
